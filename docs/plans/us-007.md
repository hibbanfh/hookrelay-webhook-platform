**Owner:** Architect · **Date:** 2026-11-19 · **Decisions:** [ADR 0016](../adr/0016-replay-as-conditional-requeue-with-the-row-trigger.md) (reuse `deliveries.trigger`, one conditional requeue in the API, worker is the authority on `enabled`, separate `DeliveryReplayer` port), [ADR 0014](../adr/0014-delivery-worker-polling-lease-and-fenced-completion.md) (claim, lease, fenced completion), [ADR 0015](../adr/0015-inspection-read-path-summaries-cursors-and-cross-module-reads.md) (`EndpointStateReader`), [ADR 0002](../adr/0002-worker-as-separate-process-same-binary.md) (API never sends), [ADR 0012](../adr/0012-google-wire-and-per-dependency-libraries.md) (Wire)
· **Contract:** `api/openapi.yaml` — `replayDelivery` (description, order of checks, 202 example, new `ReplayConflict` response; no schema shape change) · **Migration:** none · **Worker change:** none

Paths are relative to `backend/`. **Write the tests first in every step.** One route, one use case, one new port with
one SQL statement. The worker already does everything a manual attempt needs; this story only proves it end to end.

**Migration needed: no.** The replay `UPDATE` is by primary key; it touches `status` and `next_attempt_at`, which
`deliveries_due_idx` and `deliveries_endpoint_status_idx` index, so it is not a HOT update. That is the same cost as
every completion (`fillfactor = 80` already).

**Contract gaps fixed in this change** (`api/openapi.yaml`): the order of checks; that both 409s use code `conflict`
with distinct messages (new `components/responses/ReplayConflict` with three examples); the 404 message; the 202
body semantics (`pending`, `next_attempt_at` = request time, counts unchanged) with an example; concurrency (exactly one
`202`); not idempotent; endpoint disabled after the `202`; crash during a manual attempt; the body is ignored.
`DeliveryStatus.pending` and `Delivery.next_attempt_at` now mention replays.

## 2. The state change (ADR 0016 §2)

```sql
-- dispatch/data/source/delivery_replay_persistent.go (autocommit, no transaction)
UPDATE deliveries
SET status = $3, trigger = $4, next_attempt_at = $5, updated_at = $5
WHERE id = $1 AND project_id = $2 AND status IN ('succeeded', 'failed')
RETURNING id, project_id, message_id, endpoint_id, status, trigger, attempt_count,
          next_attempt_at, last_attempt_at, created_at
```

Use the existing `deliveryColumns` constant for `RETURNING` (it excludes `lease_token`). `$3`/`$4`/`$5` come from
`Delivery.Replay(now)`: `pending`, `manual`, `now` (UTC, the use case clock). The `status IN (...)` literal is the
concurrency precondition, like `status = 'pending'` in `completeFencedSQL`. `pgx.ErrNoRows` → `source.ErrNoRows`.

| Column | Effect | Why |
|---|---|---|
| `status` | → `pending` | the row is the queue (ADR 0001) |
| `trigger` | → `manual` | the worker copies it into the attempt and `ApplyOutcome` skips the planner |
| `next_attempt_at` | → `now` | due at once (`CHECK (status = 'pending') = (next_attempt_at IS NOT NULL)` holds) |
| `updated_at` | → `now` | |
| `attempt_count`, `last_attempt_at` | unchanged | manual attempt is `attempt_count + 1`; history append-only |
| `lease_token` | unchanged (already `NULL`) | `CHECK (lease_token IS NULL OR status = 'pending')` guarantees it for terminal rows |

**Race analysis**
- *Replay vs. replay:* the second `UPDATE` waits on the row lock, re-checks `WHERE` on the committed version
  (`pending`), matches 0 rows → `ErrDeliveryPending` → 409. Exactly one `202`.
- *Replay vs. claim:* disjoint predicates (`pending` vs. terminal). No interaction.
- *Replay vs. completion:* completion needs `status = 'pending' AND lease_token = $t`. A terminal row has no lease, so
  a replay can only happen after completion committed. A stale worker (lease lost earlier) fails its fenced update
  after the replay, because the token is `NULL` (or a newer one after the next claim) → `ErrLeaseLost`, nothing recorded.
- *Replay vs. endpoint disable:* not atomic (ADR 0016 §3). Disabled before the check → 409; disabled after → `202`,
  then the worker records `endpoint_disabled` and the delivery is `failed`.

### Step 2: use case (tests first: `domain/usecase/replay_delivery_test.go`, fakes in `fakes_test.go`)

`domain/usecase/replay_delivery.go`

```go
type ReplayDelivery struct {
	deliveries repository.DeliveryReader
	endpoints  repository.EndpointStateReader
	replayer   repository.DeliveryReplayer
	clock      Clock
}
func NewReplayDelivery(d repository.DeliveryReader, e repository.EndpointStateReader, r repository.DeliveryReplayer, c Clock) *ReplayDelivery
type ReplayDeliveryInput struct{ ProjectID, DeliveryID string }
type ReplayDeliveryOutput struct{ Delivery entity.Delivery }
```

Flow (guard clauses, one level): `deliveries.Get(projectID, id)` (wrap `%w`; `ErrDeliveryNotFound` passes through)
→ `ensureEndpointEnabled(ctx, d)` (`GetState(d.ProjectID, d.EndpointID)`; error wrapped; `!Enabled` →
`ErrEndpointDisabled`) → `next, err := d.Replay(clock.Now())` → `replayer.Requeue(ctx, next)` (wrap) → output the
**returned** delivery (the stored row, not `next`). No transaction: the conditional update is the guard.

| Case | Fakes | Want |
|---|---|---|
| failed, enabled | Get → failed (count 6) | `Requeue` called once with pending/manual/now, project and ID; output = row the fake returned |
| succeeded, enabled | Get → succeeded | 202 path, same as above |
| unknown or foreign | Get → `ErrDeliveryNotFound` | `errors.Is(err, ErrDeliveryNotFound)`; `GetState` and `Requeue` not called |
| endpoint disabled | GetState → `{Enabled: false}` | `ErrEndpointDisabled`; `Requeue` not called |
| endpoint disabled **and** pending | both | `ErrEndpointDisabled` (order of checks) |
| pending (waiting / leased) | Get → pending | `ErrDeliveryPending`; `Requeue` not called |
| lost race | Requeue → `ErrDeliveryPending` | `ErrDeliveryPending` |
| endpoint lookup fails | GetState → `errBoom` | wrapped `errBoom`, not a 409 |
| Get / Requeue DB error | `errBoom` | wrapped, `errors.Is` holds |

## 5. Security, limits and operability

- **Isolation:** `Get` and the `UPDATE` are both scoped by `project_id` from the auth context; foreign = unknown = 404.
- **No outbound call in the API** (ADR 0002): the API only writes the row; rule 5f proves the graph has no sender.
- **Abuse bound:** at most one queued or in-flight attempt per delivery; a replay storm on one delivery gets 409s and
  costs one indexed read each. Many deliveries replayed at once are bounded by the worker's concurrency (16). Real rate
  limits are US-012.
- **Same `webhook-id` on purpose:** receivers dedupe by it; documented in the contract (and README via tech-writer).
- **Logs:** the access log line already carries `route`, `status`, `project_id`; the worker line carries
  `trigger=manual`. No payloads logged. (Optional for US-017: `hookrelay_replays_total{result}`; not in this story.)

## 8. Risks and limits

- **Clock skew:** `next_attempt_at` is the API clock, the claim compares with the worker clock (same NTP assumption as
  publish). A skew larger than ~4 s would break the 5 s AC; the E2E runs both in one process, so it cannot catch it.
- **Backlog:** the claim is FIFO by `next_attempt_at`, so a replay queues behind older due rows. Fine for the MVP.
- **Not idempotent:** a retried `POST` after the first replay finished makes another manual attempt (PM Q24).
- **TOCTOU on `enabled`:** a disable racing the request gives `202` then an `endpoint_disabled` attempt (PM Q28).
- **Test flakiness:** the "no automatic retry" E2E waits a fixed 3 s; keep the test schedule at `1s,2s` so the wait is
  strictly longer than any retry it must rule out. The timestamp test must wait for the next second boundary, or
  `ts2 == ts1` is possible.
