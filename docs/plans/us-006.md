**Migration needed: no.** 0004 and 0005 were written with these queries in mind; every query in §3 has a matching index.

**Gaps found (all fixed by this plan or this change):**

1. **`json.RawMessage` breaks the byte-for-byte payload.** `httpx.WriteJSON` uses `json.Encoder`, which runs
   `compact` on every `Marshaler` output (whitespace removed) and escapes `<`, `>`, `&` as `<...`.
   Architecture §7.4 said "embeds the stored bytes as `json.RawMessage`". Fix: the message presenter marshals
   everything except `payload`, splices the stored bytes in, and writes the body with a new `httpx.WriteRawJSON`
   (step 5a). Test with a payload containing whitespace, key order `{"b":1,  "a":"<&>"}`, and `é` escapes.
2. **Adding `ErrNotFound → 404` to the message error table changes publish.** The table deliberately omits it today
   because an idempotent replay whose key or message is missing is a server fault (500). Fix: `PublishMessage.replay`
   converts a `ErrNotFound` from `Keys.Find` / `Messages.Get` into a new unmapped sentinel `ErrBrokenIdempotencyRecord`
   (step 2b), then `ErrNotFound` can map to 404.
3. **`dispatch` entity has no `CreatedAt`**, but `Delivery.created_at` is in the contract. Add it to the entity and to
   the claim's `RETURNING` so the worker never holds a half-filled entity (step 1a).
4. **No ID validators for `msg_` and `dlv_`.** Only `endpoint.IsEndpointID` exists. Add `IsMessageID` (message) and
   `IsDeliveryID` + `IsEndpointID` (dispatch; it cannot import the endpoint module).
5. **Contract under-specified** (fixed in `api/openapi.yaml` by this change): ordering of `MessageDetail.deliveries`,
   meaning of `last_attempt_at` and the summary counts, `response_body` bytes vs characters and `""` vs `null`,
   `response_body_truncated`, empty/repeated `status`, order of 400 vs 404 checks, cursor kinds, the attempts list
   pagination rationale, the late-commit caveat. No schema shape changed, so `make gen-api` yields only comment diffs.
6. **The planned `EndpointCatalog.GetState` would drag the endpoint repository into the worker graph.** ADR 0015
   replaces it with a separate `dispatch.EndpointStateReader` port adapted onto the existing `endpoint.GetEndpoint`.

## 3. Query shapes (all in `data/source`, every one project-scoped)

```sql
-- message: list page (no payload column: a page of 100 x 256 KB payloads would be 25 MB)
SELECT id, project_id, event_type, created_at FROM messages
WHERE project_id = $1 [AND (created_at, id) < ($3::timestamptz, $4::text)]
ORDER BY created_at DESC, id DESC LIMIT $2;                       -- messages_project_created_idx

-- dispatch: summaries for one page (ADR 0015 §1)
SELECT message_id, status, count(*) FROM deliveries
WHERE project_id = $1 AND message_id = ANY($2::text[])
GROUP BY message_id, status;                                      -- UNIQUE (message_id, endpoint_id)

-- dispatch: deliveries of one message (<= 20)
SELECT <delivery columns> FROM deliveries
WHERE project_id = $1 AND message_id = $2 ORDER BY id;            -- UNIQUE (message_id, endpoint_id)

-- dispatch: one delivery (ownership for attempts)
SELECT <delivery columns> FROM deliveries WHERE id = $1 AND project_id = $2;   -- PK

-- dispatch: endpoint deliveries; 4 constants (status yes/no x first/next page) so each has a
-- static plan on the matching index. No "($3 IS NULL OR status = $3)": pgx caches prepared
-- statements, and a generic plan for that predicate cannot use deliveries_endpoint_status_idx.
SELECT <delivery columns> FROM deliveries
WHERE endpoint_id = $1 AND project_id = $2 [AND status = $5] [AND (created_at, id) < ($3, $4)]
ORDER BY created_at DESC, id DESC LIMIT $n;                       -- deliveries_endpoint[_status]_idx

-- dispatch: attempts, oldest first, keyset on attempt_number (0 = first page)
SELECT <attempt columns> FROM attempts
WHERE delivery_id = $1 AND project_id = $2 AND attempt_number > $3
ORDER BY attempt_number LIMIT $4;                                 -- UNIQUE (delivery_id, attempt_number)
```

`<delivery columns>` = `id, project_id, message_id, endpoint_id, status, trigger, attempt_count, next_attempt_at,
last_attempt_at, created_at` (never `lease_token`). Every route is exactly 2 queries; there is no per-row query.
All reads are plain autocommit statements on the pool (no transaction, `READ COMMITTED`, ADR 0015 §4).

## 5. Security, limits and operability

- **Isolation:** every SQL statement filters on `project_id` from the auth context; the composite FKs make cross-project rows impossible. Malformed IDs are 404 before any query.
- **Untrusted content:** `response_body` and `payload` are rendered as text by the dashboard, never HTML (contract says so). `response_body` was sanitized at write time (UTF-8, no NUL).
- **Response size:** list items never carry `payload`; the largest response is one message detail (≤ 256 KB payload + 20 deliveries) or a page of 100 attempts (≤ ~420 KB).
- **DoS:** `limit ≤ 100`, cursors ≤ 512 chars, `statement_timeout = 5s`, request timeout 10 s. Every query is index-bounded.
- **Logs:** access log only; payloads and response bodies are never logged.
- **Not cached:** no `Cache-Control` change (only the secret route is `no-store`).

## 7. Risks and limits

- **Two queries, two snapshots** (ADR 0015 §4): counts may be a few ms newer than the page. Documented in the contract.
