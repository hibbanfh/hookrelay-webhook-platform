# US-005 implementation plan: retry failed deliveries with exponential backoff

**Owner:** Architect · **Date:** 2026-11-18 · **Decisions:** architecture §8.3 (state machine and retry policy), [ADR 0014](../adr/0014-delivery-worker-polling-lease-and-fenced-completion.md) (retry state lives in `next_attempt_at`, the claim does not count tries), [ADR 0001](../adr/0001-postgres-as-delivery-queue.md) (Postgres queue). No new ADR: every choice below follows from those.
· **Contract:** `api/openapi.yaml`, descriptions only (no new paths) · **Migration:** none

Paths are relative to `backend/`. **Write the tests first in every step.** US-004 already built the whole
pipeline around a `RetryPlanner` strategy wired as `NoRetry`. This story adds the real planner, a jitter port and
two validated settings, and swaps one provider. `ApplyOutcome`, `AttemptDelivery`, the SQL and the schema do not change.

## 1. Verification of the existing design (done 2026-11-18)

`entity.Delivery.ApplyOutcome` (`internal/dispatch/domain/entity/delivery.go`) was checked against every row of §8.3:

| §8.3 row | Code | Status |
|---|---|---|
| 2xx → `succeeded`, `next_attempt_at = null` | `IsSuccess()` first → `succeed()` sets `NextAttemptAt = nil` | OK, tested |
| `destination_blocked` / `endpoint_disabled` → `failed`, planner not asked | `Err.IsTerminal()` → `fail()` (`NextAttemptAt = nil`) | OK, tested (planner calls = 0) |
| other failure, `automatic`, attempts left → `pending`, `next = now + delay ± jitter` | `reschedule(p, now)` → `p.Next(AttemptCount, now)` | OK, tested with a fake planner |
| other failure, `automatic`, exhausted → `failed` | `Next` returns `false` → `fail()` | OK, tested |
| any failure, `manual` → `failed` | `d.Trigger == TriggerManual` → `fail()` | OK, tested |
| attempt numbering | `afterAttempt` sets `AttemptCount = n+1` **before** `reschedule`, so the planner gets the number of the attempt that just failed (1-based); `Delays[n-1]` is the delay after attempt `n`, exhausted when `n > len(Delays)`. The claim never touches `attempt_count` (crash = no attempt consumed) | OK, tested (`gotN == 2` after `attempt_count = 1`) |
| `next_attempt_at = null` on every terminal state | `succeed()` and `fail()` both clear it; the DB enforces it too: `CHECK ((status = 'pending') = (next_attempt_at IS NOT NULL))` | OK |
| durable retry state | `completeFencedSQL` writes `status`, `attempt_count`, `next_attempt_at`; the claim selects `next_attempt_at <= now` on `deliveries_due_idx` | OK, nothing in memory |

**Gaps found (all fixed by this plan, none in `ApplyOutcome` itself):**

1. **Jitter port location (dependency rule).** §5.4 and the old §17 put the `Jitter` port in `domain/usecase/jitter.go`,
   but `BackoffSchedule` is an `entity` (it implements `entity.RetryPlanner`). `entity` cannot import `usecase`
   (dependencies point inward). Fix: declare the port in `entity` next to `RetryPlanner`, as
   `entity.JitterSource`. `library/random` satisfies it structurally, and `wire/dispatch.go` binds it.
2. **`library/random` has no uniform float source.** It only has `Crypto.Bytes`. Add `random.Uniform` (step 1b).
3. **Config accepts a schedule with no entries.** `RETRY_SCHEDULE=","` or `" , "` splits to an empty slice with no
   error, which would silently turn retries off. **`RETRY_JITTER=NaN` is accepted** because both `f < 0` and
   `f >= 1` are false for NaN. **No upper bound per delay**, so `d × 1.1` can overflow `time.Duration` for absurd values.
4. **The reference point of the delay was not written down.** `ApplyOutcome` gets `Clock.Now()` taken *after* the
   HTTP call, so `next_attempt_at = end of failed attempt + delay × (1 ± j)`. The start-to-start gap is therefore
   `duration + delay ± jitter + ≤ poll interval`, so it is always ≥ `delay × (1 − j)`. Recorded in §8.3.
5. **E2E harness side effect.** `wire/dispatch_integration_test.go` `workerConfig` builds `config.Config` directly
   with `RetrySchedule` nil. The US-004 tests that expect `failed` after one attempt (timeout, redirect) keep passing
   only if an **empty schedule means "no retry"** in `BackoffSchedule`. `config.Load` still rejects an empty schedule
   for real processes. Make this explicit with a comment in `workerConfig`.
6. **Stale docs:** §8.2 diagram says `ApplyOutcome(policy, jitter, now)` (the real signature is
   `ApplyOutcome(result, planner, now)`), §17 says `platform/random`, `.env.example` and the OpenAPI outbound
   webhook still say "until US-005 a failed attempt is final". All fixed in this change.

## 3. Steps (paths under `internal/`)

### Step 1a: `dispatch/domain/entity` (tests first: `backoff_schedule_test.go`)

| File | Contents |
|---|---|
| `jitter_source.go` (new) | `type JitterSource interface{ Float64() float64 }`. Doc: returns a uniform sample in `[0, 1)`; it is a port so tests are deterministic and `entity` stays stdlib-only |
| `backoff_schedule.go` (new) | `BackoffSchedule{delays []time.Duration; jitter float64; source JitterSource}`. `NewBackoffSchedule(delays []time.Duration, jitter float64, src JitterSource) (BackoffSchedule, error)`: copies `delays`; rejects any delay `<= 0` or `> MaxRetryDelay` (24h, guards the float overflow), `!(jitter >= 0 && jitter < 1)` (also catches NaN), and a nil source, with `ErrInvalidRetryPolicy`. An empty `delays` is valid and means "never retry". `(s) Next(n int, now time.Time) (time.Time, bool)`: guard `n < 1 \|\| n > len(s.delays)` → `(time.Time{}, false)`; else `factor := 1 + s.jitter*(2*s.source.Float64()-1)`; return `now.Add(time.Duration(float64(s.delays[n-1]) * factor)), true` |
| `retry_planner.go` | `NoRetry` comment: "used by tests; production wires `BackoffSchedule`" |
| `errors/sentinel.go` | `ErrInvalidRetryPolicy` (only reachable if wiring bypasses `config.Load`) |

Tests (`backoff_schedule_test.go`, table-driven, `fixedJitter{u float64}` fake):
- default schedule `5s,30s,2m,15m,1h` with `u = 0.5` (factor 1): `n = 1..5` → `now + 5s, 30s, 2m, 15m, 1h`; `n = 6` → `false`; `n = 0` → `false`.
- jitter bounds with `j = 0.10`: `u = 0` → exactly `0.9 × d`; `u = 0.999999` → `< 1.1 × d` and `> 1.0999 × d`; `j = 0` → exactly `d` whatever `u`.
- empty schedule: `n = 1` → `false`.
- constructor: `0s` delay, `-1s`, `j = -0.01`, `j = 1`, `j = NaN`, nil source → `ErrInvalidRetryPolicy`; changing the caller's slice afterwards does not change the schedule.
- `delivery_test.go` add: walk with the real schedule `[1s, 2s]` and `u = 0.5`: three `ApplyOutcome` calls with `500` → `pending (next = now+1s)`, `pending (next = now+2s)`, `failed (next = nil, attempt_count = 3)`. Same walk with `trigger = manual` → `failed` at once. A `200` on attempt 2 → `succeeded`, `next = nil`.

### Step 3: `platform/config` (tests first: rows in `config_test.go`)

Replace `durations` with a dedicated `retrySchedule(name, def string) []time.Duration` and harden `jitter`:

| Variable | Rule | Error message (contains the variable name) |
|---|---|---|
| `RETRY_SCHEDULE` | unset or blank → default `5s,30s,2m,15m,1h`. Split on `,`, trim spaces, drop empty parts. **At least one entry** after that. Each entry parses with `time.ParseDuration`, is `> 0` and `<= 24h` (`maxRetryDelay`, guards the float multiply against overflow and catches typos like `1000h`) | `RETRY_SCHEDULE must list at least one positive Go duration`, `RETRY_SCHEDULE: invalid duration "x"`, `RETRY_SCHEDULE: "48h" exceeds 24h` |
| `RETRY_JITTER` | unset or blank → `0.10`. `strconv.ParseFloat`; accepted only if `f >= 0 && f < 1` (written as `!(f >= 0 && f < 1)` → fail, so NaN fails) | `RETRY_JITTER must satisfy 0 <= j < 1` |

Invalid values make `Load` return an error (all problems joined), so the process exits 1 at startup, the same as every other setting.

New test rows: default parses to exactly `[5s 30s 2m 15m 1h]` and `0.10`; `1s,2s` → `[1s 2s]`; `" 1s , 2s "` → `[1s 2s]`;
`","` → error; `"1s,,2s"` → `[1s 2s]`; `"0s"`, `"-1s"`, `"abc"`, `"25h"` → error; `"24h"` → ok;
`RETRY_JITTER` `"0"` ok, `"0.99"` ok, `"1"`, `"-0.1"`, `"NaN"`, `"Inf"`, `"abc"` → error.

## 5. Timing, concurrency, failure

- **Precision:** a retry fires at `next_attempt_at` + ≤ `WORKER_POLL_INTERVAL` (500 ms). Gaps are lower-bounded, never upper-bounded, in tests.
- **Concurrency:** unchanged. The rescheduled row is written by the fenced `Complete`, so a stale worker cannot overwrite a retry time. A retry is claimed by `SKIP LOCKED` like any due row; two workers never run the same retry.
- **Crash during a retry attempt:** the claim moved `next_attempt_at` to the lease expiry, so the retry runs again ≤ 30.5 s later and reuses the attempt number (ADR 0014). A crash never consumes the retry budget.
- **Crash between attempts:** nothing to lose. The only retry state is the row.
- **Load on a struggling receiver:** at most 6 requests per delivery over about 1h18m. Fleet-wide, retries share `WORKER_CONCURRENCY` with first attempts; jitter spreads a burst that failed together. Per-endpoint rate limiting and circuit breaking stay P2 (US-018/US-020).
- **Indexing / N+1:** retries use the existing partial index `deliveries_due_idx (next_attempt_at) WHERE status = 'pending'`; no extra query per attempt.
- **Migration safety:** no migration.
- **Config change on a live system:** a new `RETRY_SCHEDULE` applies to the next failure of every pending delivery. Already scheduled `next_attempt_at` values are kept. Shrinking the schedule makes deliveries past the new length fail at their next failure (`n > len(Delays)`), which is the expected meaning.

## 6. Risks and open points

- **4xx is retried** (backlog note: MVP retries every non-2xx). A receiver that answers `400` gets 6 identical requests. `Retry-After` and `410 Gone` are US-020.
- **Jitter is symmetric** (`±j`), not "full jitter". Enough for 6 attempts per delivery; recorded in §8.3, no ADR.
- **`maxRetryDelay = 24h`** is an architect default, not in the AC. Open question for the PM (architecture §18 Q19).
