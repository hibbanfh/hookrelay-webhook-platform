## 3. Data layer: hooks, query keys, polling

`lib/queries/keys.ts` (one factory, so invalidation is never a typo):

| Key | Hook (file) | Request | Cache |
|---|---|---|---|
| `["me","project"]` | `useEnsureProject` (exists) | `POST /v1/me/project` | `staleTime: Infinity` |
| `["project"]` | `useProject` (`lib/queries/project.ts`) | `GET /v1/project` | `staleTime: Infinity` (demo URL is config) |
| `["endpoints","list"]` | `useEndpoints` (`lib/queries/endpoints.ts`) | `useInfiniteQuery`, `limit=100` | default; at most 20 endpoints, so one page in practice; Load more still wired from `next_cursor` |
| `["messages","list"]` | `useMessages` (`lib/queries/messages.ts`) | `useInfiniteQuery`, `limit=20` | polls, see below |
| `["messages", id]` | `useMessage` | `GET /v1/messages/{id}` | polls, see below |
| `["deliveries", id, "attempts"]` | `useAttempts` (`lib/queries/deliveries.ts`) | `useInfiniteQuery`, `limit=100` | polls, see below |

Mutations (same files): `useCreateEndpoint`, `useUpdateEndpoint`, `useRevealSecret`, `useReplayDelivery`.

- **Secrets never enter the query cache.** `useRevealSecret` is a `useMutation`; the secret lives in `SecretReveal` state
  and is dropped on unmount (same rule as the API key dialog). The create response's `signing_secret` is ignored by the list
  and shown once through the same component.
- **Create** → `invalidateQueries(["endpoints","list"])`. **Toggle** → `setQueryData` on the matching item in the list
  pages from the `200 Endpoint`, then invalidate (persisted state wins). The switch is disabled while the mutation is pending.

**Polling and the 10-second replay criterion.** No push (US-019). The worker polls every 500 ms (ADR 0014), so the budget is
worker pickup + attempt duration + one UI poll.

1. `useReplayDelivery.onSuccess(delivery)` writes the returned `Delivery` (`status: pending`) into `["messages", messageId]`
   with `setQueryData`. The Replay button disables at once and polling starts without waiting for a round trip.
   Also invalidates `["messages","list"]` (summary changed). `onError` 409 → inline message from `error.message`, then
   invalidate `["messages", messageId]` (the server state was different).
2. `useMessage`: `refetchInterval: (q) => q.state.data?.deliveries.some(d => d.status === "pending") ? 1000 : false`.
3. `useAttempts(deliveryId, {status, attemptCount})`: `refetchInterval: status === "pending" ? 1000 : false`, plus a
   `useEffect` on `[status, attemptCount]` in `DeliveryCard` that invalidates the attempts key when either changes. This
   closes the race where the last attempts poll lands just before the attempt is written and the delivery then leaves
   `pending` (an in-flight attempt is not listed, per the contract).
4. `useMessages`: `refetchInterval` 5 s while any loaded message has `pending > 0`, otherwise off; `refetchOnWindowFocus`
   stays on. Refetching an infinite query re-reads every loaded page, which is also what fixes Q23 (late-committing message).

With the demo receiver an attempt takes milliseconds, so the manual attempt appears in about 1-2 s. A real receiver can take
up to `DELIVERY_TIMEOUT` (10 s) and then the 10 s target is not met; that is inherent to the receiver and noted for QA.

**N+1:** the message page fires one attempts request per delivery, in parallel. This is bounded by the endpoint cap
(`MAX_ENDPOINTS_PER_PROJECT`, 20) and only pending deliveries poll. Trade-off accepted over lazy expand because the AC asks
for every delivery's attempts on the page; an `include=attempts` API variant is the fix if the cap grows.

## 4. API errors → UI (`lib/api/errors.ts`)

`toApiError(error: unknown, status: number): ApiError` returns `{code, message, field?, status}` and never throws:
a body that is not the error shape (proxy HTML, network failure) becomes `{code: "internal", message: "Something went wrong. Try again."}`.
`fieldErrors(err, fields)` returns `{[field]: message}` when `err.code === "validation_error"` and `err.field` is one of
the form's fields, else `{}`; the caller shows anything else in the form-level alert.

| Response | Where it shows |
|---|---|
| `400 validation_error`, `field` ∈ {`url`, `description`} | under that input, `aria-invalid` + `aria-describedby` (same pattern as `auth-form.tsx`), focus moves to the first invalid input |
| `400` with `field: body` or no field, `409 conflict` (endpoint limit), `413` | form-level `role="alert"`, the API `message` verbatim (it is user-safe per the contract) |
| `409 conflict` on replay | inline next to that delivery's Replay button |
| `401`, `409 project_not_provisioned` | already handled by `client.ts` middleware (redirect / re-ensure); components show nothing extra |
| `404` on detail | "Message not found" page state |
| `502 bad_gateway`, `503 auth_unavailable`, `5xx` | page or form alert "The service is unavailable. Try again." + Retry |

Client-side checks before submit are minimal (URL not empty); the API is the source of truth for URL rules (SSRF, https in
production), so the UI never duplicates them.
