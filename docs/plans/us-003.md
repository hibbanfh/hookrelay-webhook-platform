## 2. Request handling (delivery layer)

### 2.1 Order of checks (first failure wins; the contract lists the same order)

| # | Check | Where | Result |
|---|---|---|---|
| 1 | Credential | `authed` guard (existing) | `401` / `409 project_not_provisioned` / `503 auth_unavailable` |
| 2 | Body ≤ `MAX_BODY_BYTES` (262144) | handler: `httpx.ReadBody` | `413 payload_too_large`. **Before any parsing**, nothing stored |
| 3 | One JSON object, known fields only, no trailing data, right types | `httpx.DecodeJSONBytesNamingFields` | `400 validation_error` (field named for a type error, e.g. `"event_type":1`) |
| 4 | `event_type` | `entity.NewMessage` | `400`, field `event_type` |
| 5 | `payload` | `entity.NewMessage` | `400`, field `payload` |
| 6 | `Idempotency-Key` header | presenter (count) + `entity.ParseIdempotencyKey` (shape) | `400`, field `Idempotency-Key` |
| 7 | Idempotency | `PublishMessage` in the transaction | `202` replay or `422 idempotency_key_mismatch` |

**Why the body is read whole first (step 2):** `httpx.DecodeJSON` streams, so a 300 KB body that
starts with `x` fails as `400` before the reader ever crosses the limit. The AC says an oversized
body is `413`. `httpx.ReadBody` calls `io.ReadAll` on the `MaxBytesReader` that the `BodyLimit`
middleware installed. Exactly 262144 bytes are accepted, and 262145 bytes return `*http.MaxBytesError`,
which `Responder` already maps to `413`. Reading 256 KB into memory per request is bounded by the
limit, and the payload has to be held in memory anyway.

### 2.2 Validation rules

| Input | Rule | Rejected examples |
|---|---|---|
| `event_type` | `^[A-Za-z0-9._-]{1,100}$` (ASCII only; length in bytes = characters) | missing, `null`, `""`, 101 chars, `"invoice paid"`, `"inv/paid"`, `"é"`, `"a\u0000"` |
| `payload` | present; the raw bytes start with `{`; valid JSON (`json.Valid`); valid UTF-8 (`utf8.Valid`) | missing, `null`, `[]`, `"x"`, `1`, `true`, an object with a raw `0xFF` byte inside a string |
| `Idempotency-Key` | absent, or exactly one header value matching `^[\x21-\x7E]{1,255}$` | empty value, 256 chars, a space, a tab, non-ASCII, the header sent twice |
| Envelope | `DisallowUnknownFields`, one value | `{"event_type":"a","payload":{},"x":1}`, `{...}{...}` |

**Raw payload bytes.** The DTO field is `json.RawMessage`. `encoding/json` copies exactly the
bytes of that value from the request (inner whitespace and key order kept, no leading whitespace),
so `Payload` is what the client sent. Never re-marshal it. A JSON `null` arrives as the 4 bytes
`null` (or as an empty slice when absent); both fail the "starts with `{`" rule.

**Why check UTF-8 ourselves:** `encoding/json` accepts invalid UTF-8 inside strings and
`RawMessage` keeps the raw bytes. RFC 8259 requires UTF-8, the payload is delivered with
`Content-Type: application/json`, and US-006 embeds it in a JSON response. Same bug class as
BUG-QA-010/011, so add a raw-byte HTTP test.

## 3. Transaction, idempotency and concurrency

All of this is in [ADR 0013](../adr/0013-publish-transaction-idempotency-and-outbox-ownership.md).
In short:

```
before tx : now = clock.Now().UTC().Truncate(µs); msg = NewMessage(ids.New("msg_"), ...); key parsed
tx (TxManager.WithinTx, READ COMMITTED):
  if key:   won = Keys.Reserve(record{project, key, fingerprint, msg.ID, now, now+TTL})
            if !won: existing = Keys.Find(project, key)
                     fingerprint differs -> ErrIdempotencyMismatch (rollback)            => 422
                     same             -> Messages.Get(project, existing.MessageID)  => 202 replay
  Messages.Create(msg)
  ids = Endpoints.EnabledEndpointIDs(project)          -- ≤ 20 rows, one indexed query
  if len(ids) > 0: Outbox.Enqueue(one PendingDelivery per id, IDs from ids.New("dlv_"))
commit (the deferred FK idempotency_keys -> messages is checked here)    => 202
```

- **Atomicity:** every write is inside `WithinTx`. Any error rolls back, so the client gets `500` and
  no message, key or delivery exists. Validation happens before the transaction opens.
- **Snapshot of endpoints:** under `READ COMMITTED`, the `SELECT` sees endpoints committed before it
  runs. An endpoint registered afterwards is not included (AC). An endpoint disabled a moment after
  the `SELECT` still gets a delivery, and the worker turns it into `endpoint_disabled` (US-004 AC).
- **No lock contention with endpoint writes:** the FK inserts take `FOR KEY SHARE` on the
  `projects` and `endpoints` rows. Endpoint creation takes `FOR NO KEY UPDATE` on `projects`, and
  PATCH takes `FOR NO KEY UPDATE` on `endpoints`. Neither conflicts with `FOR KEY SHARE`.
- **Concurrent identical requests:** the loser's `Reserve` blocks on the primary-key index until the
  winner commits, then returns `false`, and the loser replays the winner's message. If the winner
  rolls back, the loser reserves the key and publishes. Exactly one message either way.
- **Replay body equals the original:** both come from the same values, truncated to microseconds
  before the first response, so `created_at` serializes identically. **Truncate `now` before building
  the entity**, otherwise the first response shows nanoseconds and the replay shows microseconds.
- **Expiry:** `Reserve` takes over a row whose `expires_at <= now` (injected clock, not `now()` in SQL,
  so tests can move time). The boundary is inclusive: at exactly 24 h the key is free.
- **Statement count:** 4 on the happy path (reserve, insert message, select endpoints, insert
  deliveries), 3 without a key, 3 for a replay (reserve, find, get). No N+1: deliveries are one
  `INSERT ... SELECT FROM unnest($1::text[], $2::text[])`.
- **Isolation level:** keep `READ COMMITTED`. Under `REPEATABLE READ` the loser would get a
  serialization error instead of seeing the winner's row.
- **Timeouts:** the 10 s request timeout and the 5 s `statement_timeout` bound a loser waiting on a stuck
  winner. The result is `500`, and a retry with the same key is safe.

## 5. Security, limits and operability

- **No outbound I/O:** the message module has no HTTP client dependency, and the API graph has no
  `Sender` (ADR 0002). Publishing to offline receivers is a pure database write.
- **Logs:** never log the payload or the idempotency key value (a key may embed customer IDs). Log the
  message ID and project ID at most. A test asserts that the payload is absent from the log buffer.
- **Tenant isolation:** `project_id` comes only from the guard. Every query is scoped by it. Composite
  FKs make a cross-project delivery impossible in the database. Keys are scoped by the primary key.
- **DoS:** 256 KB body cap, 10 s request timeout, 5 s statement timeout, ≤ 20 endpoints per project
  (so ≤ 20 deliveries per publish). There is no publish rate limit until US-012; see open question 3.
- **Storage growth:** messages, deliveries and keys grow without bound until US-016.

| 9 | Same key + identical request within 24 h → same response, nothing new | UC "live key, same fingerprint"; INT `Reserve` live → false; **E2E `testIdempotentReplay`**: the two bodies are **byte-identical**, `Idempotent-Replayed: true` on the second only, still 1 message and its deliveries; INT expiry: at `now = expires_at` a new message is created |
| 10 | Same key + different body → `422 idempotency_key_mismatch`, nothing new | UC; E2E (different `event_type`; different payload; payload differing only in whitespace (Q7)), row counts unchanged |
| 11 | Two concurrent identical requests → exactly one message | **INT race** (10 goroutines, real tx, `-race`); E2E variant with 10 parallel HTTP requests through the router → one distinct `id`, `count(*) = 1` |
| 12 | Same key in two projects → one message each | INT `Reserve` per project; E2E with keys A and B → two different IDs, each project's deliveries only to its own endpoints |

**Cross-cutting (backlog conventions), E2E:** no credential → `401`; both credentials → `401`
(identical body); a valid session publishes and is scoped to its own project; a session without a
project → `409 project_not_provisioned` (existing guard, one row); a Neon outage → `503` (existing
guard, one row); `GET /v1/messages` → `405` with `Allow` until US-006.

**US-025 carry-forward (cross-user `404`):** it does not apply to this story. `POST /v1/messages` takes no
resource ID, so there is nothing to answer `404` for. The isolation that does apply is tested: user A's
session publish creates deliveries only to A's endpoints, never B's (E2E, session A + API key B). The
`404` clause stays open for **US-006** (`GET /v1/messages/{id}`, `GET /v1/deliveries/{id}/attempts`,
`GET /v1/endpoints/{id}/deliveries`) and **US-007** (`POST /v1/deliveries/{id}/replay`).

## 7. Risks and limits

- `message/data` is coupled to three `endpoints` columns and the initial-state `deliveries` columns
  (ADR 0013). A rename in `endpoint` or `dispatch` must update `fanout_persistent.go`. The integration
  test catches a mismatch in CI.
- A stuck winner holds the key row lock. Waiters fail at the 5 s statement timeout with `500`; a retry
  with the same key is safe.
- A whitespace-only payload difference is a `422` (strict fingerprint, Q7).
- No rate limit on publish until US-012. On the public demo, the shared key lets anyone fill the table
  (≤ 256 KB × requests). Retention (US-016) and Q1/Q4 cover cleanup.
- The migration was written without being run (no Docker available to the architect). Step 4's
  up/down/up test is the first real check: run it before anything else in that step.
