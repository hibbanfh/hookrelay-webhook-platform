# ADR 0012: Google Wire for the object graph; one library package per dependency

- **Status:** Accepted. Supersedes the "Manual dependency injection" part of [ADR 0005](0005-clean-architecture-and-manual-di.md). The dependency rule, caller-owned ports and the context-carried unit of work stand.
- **Date:** 2026-11-09
- **Story:** US-002 (lands first, as a behaviour-preserving refactor)

## Context

ADR 0005 chose hand-written wiring because the graph was about 100 lines. Five modules are planned,
each with several use cases per file (ADR 0010), a shared auth guard and cross-module adapters.
`cmd/server` already holds a `projectModule` struct and helper functions only to carry dependencies
around, and every new use case adds more of this by hand.

Cross-cutting code also sits in one `internal/platform` tree. It mixes third-party and I/O
dependencies (Postgres, clock, IDs, randomness, logging) with HTTP and process concerns.

The owner decided to move to Wire and to one package per dependency. This ADR records how that
fits the rules we already enforce.

## Decision

### 1. Wire builds every process graph, once, at the composition root

`github.com/google/wire` v0.7.0, in a new top-level package:

| File | Build tag | Contents |
|---|---|---|
| `backend/wire/wire.go` | `wireinject` | Injector declarations only |
| `backend/wire/wire_gen.go` | `!wireinject` | Generated by Wire, committed |
| `backend/wire/<module>.go` | none | The module's provider set, its `wire.Bind`s and thin provider functions |
| `backend/wire/router.go` | none | Mux, route registration, middleware chain (same order as before) |
| `backend/wire/options.go` | none | Maps `config.Config` to each library's `Options` |
| `backend/wire/adapters.go` | none | Cross-module port adapters (moved from the planned `cmd/server/adapters.go`) |

Injectors:

| Injector | Returns | Used by |
|---|---|---|
| `InitializeAPI(ctx, cfg)` | API struct (router + logger), cleanup, error | `hookrelay api`, called once |
| `InitializeRouter(cfg, log, pool)` | `http.Handler` | Tests only: same module sets, but the caller supplies a log buffer and a lazy pool |
| `InitializeWorker(ctx, cfg)` | worker struct, cleanup, error | `hookrelay worker` |
| `InitializeSeed(ctx, cfg)` | seed struct (use case + logger), cleanup, error | `hookrelay seed` |

**Subcommands.** `api`, `worker` and `seed` each own an injector, so there is one wiring style and
`seed` does not need a hand-built copy of the project graph. Each injector supplies its own pool
size and process name. An injector only pulls in what it needs, and Wire rejects unused sets, so
"the API process never constructs a `Sender`" (architecture 8.1) becomes a property of the graph.

**`migrate` stays a plain function call.** It has no object graph and must not open an application
pool. It calls `library/postgres.Migrate` directly. `main.go` still only dispatches subcommands.

Wire is a build-time tool. Domain constructors stay plain Go and know nothing about it.

### 2. One package per dependency under `internal/library/`

Each is small, exposes `ProviderSet`, and takes its own `Options` struct.

| Package | From | Provides |
|---|---|---|
| `library/postgres` | `platform/postgres` | Pool (with cleanup), `Migrate`, and new in US-002: `TxManager`, `Executor` |
| `library/clock` | `platform/clock` | System clock |
| `library/ids` | `platform/ids` | ULID generator |
| `library/random` | `platform/random` | `crypto/rand` source |
| `library/logger` | `platform/logging` | `*slog.Logger` |
| `library/httpclient` | new (extracted from `cmd/server`) | Outbound `http.Client` with a timeout and no redirects |
| `library/secretbox` | new (was planned as `platform/crypto`) | AES-256-GCM seal and open with key versions |
| `library/netguard` | new (was planned as `platform/netguard`) | SSRF policy, ranges and DNS resolver; the dial guard joins in US-004 |

`internal/platform` keeps what is not a swappable dependency: `config`, `httpx`, `auth`, `health`.

**No single `Library` interface.** A god interface would make every use case depend on everything
and would make fakes large. Each domain keeps its own small ports (`Clock`, `IDGenerator`,
`RandomSource`, `TxManager`, `URLPolicy`, `SecretCipher`), one per file. Library types satisfy them
structurally, so port signatures use only stdlib and domain types.

**A library knows nothing about the application.** It imports the stdlib, its own third-party
package and `google/wire`. It never imports a module, `platform/config`, another library or
`backend/wire`. Where one library needs another (the ID generator needs a clock) it declares a
small local interface, and the binding is made in `backend/wire`.

**Domain errors do not leak into libraries.** A library cannot return `ValidationError`, so a port
whose result needs a domain error returns a plain `error`, and the use case translates it (see
`URLPolicy` in `docs/plans/us-002.md`).

### 3. Where provider sets live, so the dependency rule holds

- `library/*` sets contain only that library's constructors. **They contain no `wire.Bind`**,
  because binding a library to a domain port would make the library import the domain.
- All `wire.Bind`s and all module sets live in `backend/wire`, the composition root. It is the only
  package besides `cmd/server` that may import `data/*` and `delivery/presenter`.
- Modules do not get a `wire.go` inside `internal/<module>`. A module-level package would import its
  own `data` and `delivery`, which `depguard` forbids, and Wire would become a dependency of the module.
- `backend/wire` sits outside `internal/`, so the `**/internal/**` depguard globs do not apply to it,
  while it can still import `hookrelay/internal/...` because it is inside the same Go module.

The rule becomes: `delivery -> domain/usecase -> domain/* <- data`, and **only the composition root
(`cmd/server`, `backend/wire`) sees everything**.

Provider functions handle whatever Wire cannot resolve by type. Plain values such as `bool` or
`string` would collide, so `options.go` and the thin providers read them from `config.Config`.

### 4. Coexistence with depguard and `check-layers.sh`

| Concern | Rule |
|---|---|
| `wire_gen.go` | Has the standard `Code generated ... DO NOT EDIT` header, so the existing `exclusions.generated: lax` setting skips it |
| `wire.go` | Excluded from normal builds and linting by its build tag. `panic(wire.Build(...))` never compiles into the binary |
| Other `backend/wire/*.go` files | Normal code: fully linted, normal flat-control-flow rules |
| Argument limit (revive, 4) | Providers with more inputs take a struct filled by `wire.Struct` |
| `depguard` additions | `library-no-app` (a library must not import modules, `platform` or `backend/wire`); `hookrelay/wire` denied under `**/internal/**`; `platform-no-domains` also denies `library`; `data/source` may import only `library/postgres`; `data/repository`, `data/neonauth` and `delivery/presenter` deny `library`; the `platform/postgres` entry is renamed; ADR 0010's per-module block is copied for `endpoint` |
| `check-layers.sh` additions | `data/source` allow-list becomes `library/postgres`; library packages checked for the same no-app rule; nothing under `internal/` imports `hookrelay/wire`; no module imports `google/wire` |
| Proof | As with earlier rules, plant one violation per new rule and confirm it fails before committing |

### 5. `wire_gen.go` is committed and CI proves it is current

- Committed, so `go build`, the Dockerfile and a fresh clone need no generator, and reviewers can read
  the resolved graph in the diff.
- The tool is pinned in `backend/go.mod` with a `tool` directive, so the library and generator share
  one version: `go tool wire gen ./wire`.
- `make wire` regenerates it. `make wire-check` and a CI step, placed before lint, run the generator
  and then `git diff --exit-code -- wire/wire_gen.go`. A stale file fails the build.

## Alternatives considered

| Option | Why not |
|---|---|
| **Keep manual DI** | Still simple and compile-checked, and it was the right call for one module. The owner chose to stop paying the per-use-case wiring cost before four more modules arrive. |
| **`uber-go/fx` or `dig`** | Graph errors appear at runtime through reflection. Wire fails at build time and produces plain Go that can be read in a diff. |
| **Provider sets inside each module** | Conventional in many Wire projects, but it needs the module to import its own `data` and `delivery` from one package, which breaks a mechanically enforced rule. |
| **`wire.Bind` inside each library** | The library would import domain ports, so the dependency would point the wrong way. |
| **Do not commit `wire_gen.go`** | Every build, including Docker, would need the generator, and the graph would disappear from code review. |
| **Wire only the API, keep worker and seed manual** | Two wiring styles, and `seed` would duplicate the project providers. |
| **Wire `migrate` too** | Nothing to inject, and it would pull in a pool it must not use. |
| **Keep everything in `internal/platform`** | One broad package tree with no per-dependency rule. Separate packages let `depguard` allow exactly `library/postgres` in `data/source`. |

## Consequences

- Positive: adding a use case means adding one line to a set. Missing or unused dependencies fail at
  generate time, and each process's graph is explicit in `wire_gen.go`.
- Positive: `data/source` can reach only the Postgres library, which is a narrower rule than the
  previous "any platform package".
- Negative: one more build step and one more thing to learn. Wire's errors can be hard to read.
- Negative: `backend/wire` is a large package that knows every module. That is its purpose, and no
  other package may import it except `cmd/server`.
- Negative: each library exposes a package-level `ProviderSet` variable. It is an immutable
  descriptor with no state, and it is the one accepted exception to "no globals".
- Negative: `github.com/google/wire` links into the binary because non-tagged files call
  `wire.NewSet`. The package is a few empty stubs, so the cost is negligible.
- Migration: the refactor must not change behaviour. Existing tests keep their assertions, and only
  import paths and the way they obtain the handler change. `docs/plans/us-002.md` orders this first.
